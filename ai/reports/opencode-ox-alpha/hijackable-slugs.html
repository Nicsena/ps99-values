Hijackable Slugs — Variant-Prefix Shadowing

From-scratch inconsistency audit · measured against data/ps99.db (16,314 items) · 2026-08-24 · companion: inconsistency-audit/hijackable-slugs.md · dataset: data/reports/hijackable-slugs.json

16,314 items scanned 30 named Golden/Rainbow/Shiny … 5 actually shadowed 25 resolve correctly

The mechanism

Detail URLs are parsed by splitDetailSlug() (src/util/slug.ts:45-68), which generates resolution candidates in this order:

58push(parts.slice(0, 2).join('-'), parts.slice(2).join('-'));  ← 2-token variant (shiny-golden-…)
61push(parts[0], parts.slice(1).join('-'));                     ← 1-token variant (golden-… / shiny-…)
63push('', parts.join('-'));                                    ← whole slug as literal item name — LAST

The route (src/routes/pages.ts) resolves candidates in order and serves the first whose remainder slug matches an existing item. Consequence: any item whose name literally begins with "Golden ", "Rainbow ", or "Shiny " is shadowed whenever the stem (name minus the prefix word) matches another item — the URL serves that other item's variant instead, and the literal item is unreachable at its natural address.

Corrected count — why 30 was wrong

Correction: the earlier audit stated "30 live items named Golden/Rainbow/Shiny … are hijackable." Re-measured properly: 30 items carry such names, but only 5 are actually shadowed — for the other 25 (e.g. Golden Fishing Rod, Shiny Hunter, Rainbow Eggs, Shiny Flag), no stem item exists, so the whole-slug fallback resolves them correctly. The original number counted URLs starting with a variant token, not URLs that resolve to the wrong item.

What the original "30" actually counted — and what the real number is

The original claim counted every row whose name starts with Golden/Rainbow/Shiny — including variant rows (Rainbow-Golden-Retriever etc.) that share a name with their base item. After filtering to base rows only (variant=0, shiny=0), there are 23 uniquely-named items. Of those, 5 are shadowed (their stem item exists, so the variant-prefix candidate wins and the literal item is unreachable) and 18 resolve correctly via the whole-slug fallback. Why "Golden Retriever" is safe but "Golden Cove Lockpick" is not: the hijack fires only when the stem (name minus the variant word) matches another existing item. "Golden Retriever" → stem "Retriever" → no item named "Retriever" exists, so the whole-slug fallback resolves it. "Golden Cove Lockpick" → stem "Cove Lockpick" → that item exists, so the variant-prefix candidate wins first and the lockpick item is unreachable.

Reading it: Rainbow Hoverboard is a genuine base item in Hoverboards (variant=0) — yet its URL /items/rainbow-hoverboard is parsed as the rainbow variant of Hoverboard. Same for the three Golden MiscItems and Rainbow Mini Chest. The rows themselves are fine; only the URL parser misroutes them.

Fix

One ordering change: try the whole-slug exact match first in the route's candidate loop (or probe findItemBySlug(wholeSlug) before iterating splitDetailSlug candidates), falling back to variant-split candidates only when the whole slug matches no item. After the fix: all 5 shadowed items become reachable, and no existing variant URL changes (variant URLs whose stem item doesn't exist behave identically). Verify with the reproduction below.
