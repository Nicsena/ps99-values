Methodology — from scratch, both cache modes, everything re-measured

This audit re-derived all conclusions from direct measurement. The server was rebuilt and exercised in both cache modes using CACHE_DISABLED: Phase A with the cache enabled (Redis flushed to zero keys — every cold is a true cold), Phase B with CACHE_DISABLED=true (every request hits SQLite; two passes). All 17 endpoints measured cold and warm, three times. SQL shapes timed via the sqlite3 CLI with EXPLAIN QUERY PLAN. Tie populations, value storage types, totals-path behavior, per-table storage (dbstat), WAL state, and hourly growth all re-measured. One independent read-only subagent audited the server code (29 findings, verified against source before inclusion); two additional subagent lenses failed on provider network errors and were covered by direct measurement.

Live state during measurement: DB 69 MB (+WAL 7.8 MB) · 65,062 RAP · 240,832 exists · 16,314 items · 15 enabled collections · last sync 2026-08-24 06:00 UTC. The instance has run overnight and all day — this is the "plenty of data" state.

Executive summary

Confirmed: cache warm = 1.2–2.6 ms; uncached = 0.78–1.04 s per listing endpoint (~400–600×), and the gap is CPU-bound — a fully warm repeat costs the same as the first.

Mechanism: every uncached listing/search/detail request re-aggregates all 240,832 exists + 65,062 RAP snapshot rows through HAVING MAX(captured_at) CTEs plus a 190k-row window sort — measured 368–417 ms each in SQL, 0.78–1.04 s end-to-end in-app, synchronous on the event loop.

Growth: ingest is ~14k exists + ~2k RAP rows/hour. The cold rebuild crossed the 2 s budget ~1 day after data collection began and is projected at ~38 s in 30 days / ~114 s at 90-day retention. The cache hides this only per key, per 15-minute window.

Also measured this pass: a totals query over the large-magnitude Coins family returned 4.42 × 10¹⁰ while the true per-row latest is 8.47 × 10⁴⁶ — the HAVING-MAX arbitrary pick serving stale values on the totals path (large values are legitimate upstream data: Psychic Seal in the trillions, Coins combined across three categories). Plus: exists values above int64 are stored as REAL inside INTEGER-typed columns.

W1

Why it got slower overnight?

MEASURED MECHANISM

Four measured facts combine into the slowdown. None is a leak, decay, or mystery — each was re-measured this pass:

Fact 1 — every uncached request re-aggregates the whole history

The listing page runs latest (GROUP BY over all 65,062 RAP rows), latest_exists (GROUP BY over all 240,832 exists rows), and hour_exists (a ROW_NUMBER window over ~the whole exists table). The count query re-runs the first two. Fresh timings: listing 368 ms + hour window 417 ms + count — inside the app with serialization = the measured 0.78–1.04 s.

Fact 2 — history grows every hour the sync runs

Measured overnight+day: ~2,000 RAP + ~8,000–11,000 exists rows/hour, change-only deduped. The CTEs' input is the table, so per-request cost is a linear function of table size: cost(today) = cost(yesterday) × rows(today) ÷ rows(yesterday).

Fact 3 — the cache converts "always slow" into "slow once per key per TTL"

Warm hits bypass SQL entirely (1.2–2.6 ms). But every distinct parameter combination is its own key, each pays the full cold cost once per TTL window (900s lists / 300s search / 3600s detail), and the hourly sync changes data without invalidating anything — the first request after each expiry pays the full growing price again.

Fact 4 — the SQL runs on the event loop

better-sqlite3 is synchronous: the 0.8–1.0 s query blocks all request handling. During the sync's insert phase, concurrent warm requests measured up to 1.10 s extra stall. One cold rebuild per popular key per TTL is enough to make the whole site feel sluggish during the expiry cascade.

The compounding: the tables grew ~24k rows overnight. Every cache expiry this morning paid 10–20% more than last night. At the current change rate the cold cost doubles roughly every 1–2 days — the exact "fine yesterday, slower today" trajectory.
W2

How the inconsistency caused the performance problem

CONNECTION

The performance issue is not one bug — it is the predictable output of several unresolved inconsistencies, each mapping onto a term of latency ≈ O(snapshot rows) × uncached requests:

1 · The unfinished variant-per-row migration forces full-table reconstruction

Variant identity lives in snapshots (pt/shiny columns, item_key strings) rather than being fully resolved at write time, so the read path must reconstruct "latest value per item-variant" by grouping the entire history on every request. The sync already computes exactly this data for dedupe — and discards it. A maintained latest-values table would reduce every listing/detail/similar query to PK lookups.

2 · The cache layer was built and left unwired

Invalidation helpers exist with zero callers; detail TTL (3600s) equals the sync cadence; four key families with hand-bumped version prefixes. The cache works mechanically (1.2–2.6 ms warm, verified) but the freshness contract is "whatever the TTL leaves," which is why correctness keeps deferring to it instead of fixing the queries.

3 · Dead config and dead controls hide the levers

SYNC_CRON is parsed, defaulted, and test-pinned but consumed by nothing — the live schedule comes from DB settings and job defaults. Cron runtime controls are tested but unrouted. The ingest rate driving the growth is not actually tunable without editing code.

4 · The magnitudes outgrew the storage model

Exists values now legitimately span 1 → 8.47 × 10⁴⁶ (combined-across-categories figures), stored as REAL inside INTEGER-typed columns and summed in SQL — where the HAVING-MAX arbitrary pick demonstrated a live totals query returning 4.42 × 10¹⁰ against true per-row latest values of 8.47 × 10⁴⁶. The storage/format model predates the data's dynamic range.

Net: every inconsistency is individually defensible as "works today" — together they are the performance problem. The roadmap below is ordered so each fix also retires an inconsistency.

Event-loop blocking — live stall tests

SYNCHRONOUS DRIVER

better-sqlite3 executes inline on the Node event loop: every query blocks ALL request handling for its duration. Measured during a live sync on the CACHE_DISABLED server (pure DB, no cache):

PhaseObserved behavior
Upstream fetch phase (~first 8–10 s)Non-blocking — requests served normally (2–4 ms)
Insert phase (500-row chunks)Concurrent requests stall behind chunk commits — previous busy-hour measurement: 1.10 s; this quiet-hour run inserted 1,072 + 4,808 rows with the stall window between samples
Steady state after sync2–4 ms
Also measured: the sync's own res.json() + zod parsing of multi-MB upstream bodies is a synchronous event-loop spike each hour, coinciding with the DB write phase. At 90-day retention the insert set and prune DELETE both scale up — the stall lengthens linearly.

Growth projection — cold listing cost vs retention horizon

CACHE BREAK-POINT ~1 DAY
The cache break-point: the 900s TTL hides the cold cost only if one rebuild per 15 min stays acceptable. The cold rebuild crossed the 2 s budget roughly one day after data collection began; at 7 days each rebuild stalls the event loop ~9.6 s, and multiple keys expiring per hour makes users hit multi-second stalls continuously. Only the structural fix changes the curve's shape.
